# AI Design Workflow System 设计文档审查报告

审查时间：2026-06-04
审查对象：`docs/design-ai-design-workflow-system.md`
审查方式：对照本仓库真实的 Impeccable 产物（`DESIGN.md`、`PRODUCT.md`、`.impeccable/`、已有 ~15 对 `design-<flow>.md`/`.html`）核验，不只读文档自述。

## 总评

方向对，自我审视水平高于一般设计文档，"编排 Impeccable 而非重造"的判断正确。

结论：**有条件通过。** 批准方向 + 阶段 0（手工验证链路）；阶段 1 的自动 gap loop 和 live 按现在的写法**先不批**，要先补齐下面的命门和几个安全契约。

## 一、命门：整套系统押在"设计稿审查门"是否可信

这是全文最重要的一点，文档没抓住。

链条是这样的：

```
DESIGN.md ──严格执行──▶ HTML 设计稿 ──审查门──▶ 被祝福的设计稿 ──▶ 生码 ──▶ gap 校验
```

下游每一步都默认"被祝福的设计稿是对的"，凭的就是中间那道审查门。**门不可信，下游全是建在沙子上，这道评审就是徒耗 token。** 所以系统成败押在这道门上。

文档缺的就是这道门的"可信契约"。6.2 只说了"LLM 评审 + detector"，没说什么情况算不通过、判得稳不稳。

该补的方案——审查门分两层：

1. **死规矩层（程序查，跑十遍一个样）**：颜色/圆角/间距用没用对 `DESIGN.md`、空/加载/错误这些状态画没画、detector 反模式。不过直接打回，AI 都不用上。
2. **判断层（AI 只判一件事）**：这页到底有没有解决需求里要解决的问题（信息架构、主路径、产品命题）。AI 每条意见必须指到"哪个屏、哪句话"，指不出实锤的不算数。

通过线：**死规矩全过 + 判断层挑不出一条有实锤的致命问题**。分数（比如 21/40）只当参考——真正拦人的是那句"产品命题错了"，不是那个数。

人来兜底：steward 定期抽查这道门的判决，门放过了人会否的、或拦了人会放的，就回去调。门靠"判得准的历史"挣信任，不是一上来就信。

> 本仓库那份真 critique 正好是证据：确定性扫描啥也没查出来（detector 干净），真正的问题是它用人话判出来的——"套着新壳的旧遥测仪表盘，产品命题错了"。机械层必要但永远不够，真正的评审价值在判断层。

## 二、"16.3 当前没有发现的硬伤"必须删改

一份认真的架构文档，不该在最高风险的三块（审查门、自动改码、移动端 live）都没验证时，给自己盖一个"无硬伤"的章。把第一节的命门、以及下面第三、第四节的问题提上来，替掉这一节。

## 三、自动改代码缺安全契约（第 11 节 / 阶段 1）

这是整套里最危险的一步——AI 动你的代码。风险：改一处坏一处，越改越乱，或者为了糊弄检查硬写死。

该补的安全契约：

1. 只准它自动改"死规矩"那类（有标准答案、一眼能验对错）；
2. "对不对路"那类判断问题，不准自动改，留给人；
3. 每改一轮，重跑一遍死规矩检查，毛病数必须比上轮少；不少就停、回滚、交人；
4. 每个改动单独能撤（一个 patch 一件事），坏了单独退；
5. 最多三轮封顶，到顶就停。

## 四、live 移动端：病根没诊断，"慢"的问题目前没方案

文档里 live 出现 20 处，全是"想要什么"（H5-first、本地 patch、knobs、PatchIntent），**没有一处点出病根**：Impeccable 的 live 是往 `index.html` 的 `</body>` 前注入一段脚本来改页面（`.impeccable/live/config.json` 里的 `insertBefore: "</body>"` 就是那个注入点），它面向 PC，移动端这套注入链路又长、体验又差。

方向（**纯加法，功能只加不减**）：原来"圈任意一块 + 说任意一句 + 模型给你改"的能力全留；旁边再加常见微调（间距/字号/颜色/圆角）的快捷旋钮，作为多给一条快路，不堵模型那条；同样的能力换个不挡手机屏的呈现。

**诚实交代：live "慢 / 链路太长"这个具体问题，目前没有成熟方案，需要单独立项研究。文档不该把它当成已经解决的事。**

## 五、gap 校验：拿什么当标准、怎么对上号

- **截图像素比对不能当主检查。** 设计稿是套手机壳模板（iPhone 边框、状态栏）生成的，实现是没这层壳的真路由，两张图比像素，比出来大半是边框和渲染噪声，不是设计差异。主检查应该是"页面有没有守 `DESIGN.md` 的规矩、该有的状态在不在、结构对不对"，截图降级成给人看的佐证图。
  > 文档 16.2 自己已经承认"只做 screenshot diff 不可靠"，但 11.1 和阶段 0 又把它当主检查——自相矛盾，要改过来。
- **"实现页面对应设计稿哪个屏"不用搞映射表。** 写 `docs/design-<flow>.md` 的时候顺手写一句"这个 flow 做在 `/sdd/skills`"，机器就去那个网址比。

## 六、登录不是瓶颈（澄清）

这项目登录就是 POST 账号密码、服务器塞一个签名 cookie 回来，而且中间件只拦 `/api/*` 接口、不拦前端页面。普适做法是**复用人已经登录好的那个会话**，不替它登录——这样不管登录环节多奇葩（SSO、2FA、扫码）都不关 gap 检查的事。文档把"实现页面 URL"当免费输入可以，但要写明前置一步：先拿到一个已登录的浏览器会话。

## 七、范围与笔墨分配

- 文档写成绿地方案，但这套模式（`DESIGN.md` + ~15 对 `design-<flow>.md`/`.html` + `.impeccable`）**已经在本仓库生产里跑着了**。最强的验证数据就在手边，文档没做任何回顾。阶段 0 应该改成"从已有这十几对里抽经验教训"，而不是"另选一个仓库从头试"。
- 阶段 0 本质就是"用现有 skill 手工跑"（brainstorming + grill-me + impeccable），近乎零新工程。真正的工程风险全在阶段 1+ 的编排器和 gap 引擎——而文档恰恰这两块写得最薄，却花大篇幅写概念和权威角色。笔墨该挪到风险所在的地方。

## 八、9.2 权威角色模型是过早抽象

文档前提是"一个人能跑完整个流程、角色可模糊"，却又给了 owner / agent / Design steward / 实现 agent 四角色审批矩阵——在 MVP（CLI + 本地 HTML）里没有执行面。保留 9.3 的更新门禁条件（写得好、可证伪），删掉 9.2 的角色排场，等阶段 3 平台化再引入。
